# 项目完成报告

## 基于 MongoDB 的在线问卷系统


项目的三个主要优化：

| 优势 | 具体体现 |
|---|---|
| 数据结构不是简单平铺 | 题目、选项和跳转规则内嵌在问卷文档，答卷独立保存；稳定 ID 避免排序和删题后规则失效 |
| 跳转不是硬编码 | 规则存为 `rules` 数据，按优先级求值；服务端提交时重新走路径。 |
| 数据库能力 | MongoDB Validator、版本索引、聚合统计和 `explain` 执行计划都有实际验证 |

## 1. 项目目标

实现一个简化版在线问卷系统：注册用户创建问卷，通过链接分发，填写者按顺序作答并根据规则跳转，提交后由创建者查看统计。

项目的关键约束：
- 使用 MongoDB，不使用关系数据库和 JOIN。
- 模块必须能独立扩展，不能把所有逻辑写在一个文件里。
- 跳转规则由问卷数据配置，不能写死在 Python 的 `if/else` 中。
- 必填、答案类型、重复提交和统计口径必须由服务端保证。

## 2. 系统设计

系统采用模块化单体：一个 Flask 应用、一个 MongoDB 数据库，不拆微服务。

| 模块 | 职责 |
|---|---|
| `auth` | 注册、登录、密码哈希、所有者判断 |
| `surveys` | 问卷创建、列表、状态、分享码、截止时间 |
| `questions` | 四种题型、选项、答案校验 |
| `logic` | 规则保存、条件求值、下一题计算、路径重放 |
| `publishing` | 发布、公开链接、关闭和截止判断 |
| `responses` | 提交令牌、匿名/重复填写策略、答卷保存 |
| `analytics` | 整卷和单题统计 |
| `common` | 数据库、错误、CSRF、时间、随机 ID |

路由层只处理 HTTP，业务逻辑在 `service.py`，MongoDB 查询在 `repository.py`。因此规则求值和统计可以脱离页面单独测试。

问卷状态：

```text
draft → published → closed
```

草稿仅所有者可编辑；发布后链接可填写；关闭或超过截止时间后拒绝提交。状态修改只发生在问卷/发布模块。

## 3. MongoDB 设计

系统使用三个集合：

| 集合 | 内容 |
|---|---|
| `users` | 用户名、密码哈希、注册时间 |
| `surveys` | 问卷元数据、题目、选项、规则、状态和分享码 |
| `responses` | 答案、访问路径、提交身份和提交令牌 |

嵌套关系：

```text
surveys
├─ questions[]
│  ├─ options[]
│  └─ config{}
└─ rules[]
   ├─ when.clauses[]
   └─ action{}

responses
├─ answers[]
└─ visitedQuestionIds[]
```

题目和规则内嵌在问卷中，读取一次问卷就能拿到完整内容；答卷独立保存，避免多人填写时争抢同一文档。`ownerId` 和 `surveyId` 是应用层文档引用，不使用关系表。

本版还增加了：

- MongoDB `$jsonSchema` Validator，拒绝非法状态和缺少提交令牌的答卷。
- 按 `shareCode`、`ownerId`、`surveyVersion`、`submittedAt`、题目 ID 等建立的索引。
- `surveyVersion` 和 `visitedQuestionIds`，保证版本区分和统计分母正确。
- `participantKey` 和 `submissionToken`，分别处理同一身份限制和双击/重试幂等。

## 4. 跳转设计

跳转规则是数据，不是代码：

```text
来源题 fromQuestionId
优先级 priority
条件 when.clauses
目标题 targetQuestionId 或结束
```

执行顺序：
1. 按优先级检查。
2. 第一条匹配规则生效。
3. 没有匹配时进入下一题。
4. 最后一题或结束动作终止。
5. 只允许跳到后续题，避免循环。

前端负责即时体验，服务端在提交时用最终答案重新计算路径。服务端只校验实际访问到的必填题，并丢弃被跳过题的答案。这样既支持跳转，也能防止用户修改 JavaScript 伪造路径。

## 5. 校验设计

| 题型 | 主要限制 |
|---|---|
| 单选 | 必须选择合法选项；必选不能为空 |
| 多选 | 选项合法且不重复；检查最少/最多选择数 |
| 文本 | 去首尾空白；检查最少/最多字数 |
| 数字 | 检查有限值、最小/最大值和是否整数 |

发布前还会检查：问卷非空、题目/选项 ID 唯一、规则目标在当前题之后、操作符与题型匹配、优先级不重复。提交接口再检查问卷状态、截止时间、匿名策略、身份、必填和答案类型。

## 6. AI 使用过程

AI 主要承担实现代码的工作，搭建了 Flask 骨架、PyMongo repository、页面模板、规则和统计初稿，也生成了测试脚本及部分文档。

AI 的初稿也有明显问题：早期倾向于把功能写在一个文件里，架构不够完整；空问卷可以发布；创建问卷后返回列表而不是出题页；测试用例最初也缺少“输入、输出、结果”这些必要列。

所以在 AI 草稿基础上，我主要进行拆分模块、补充发布校验、把创建后的流程改为进入题目管理页、增加重复提交约束，并把测试表改成步骤、输入、预期输出、实际输出和结果。其中进行的设计修改包括：
- 问卷统一放在一个集合，题目和规则内嵌
- 分享链接使用 `/survey/<分享码>`
- 匿名和重复填写分别设置
- 必填只对实际访问到的题生效
- 统计区分访问人数和回答人数

详细 Prompt、生成结果和修改记录见 `docs/11-AI使用日志.md`

## 8. 遇到的问题和解决

| 问题 | 解决 |
|---|---|
| 创建问卷后进入列表 | 创建成功后重定向到 `/surveys/<id>`，增加对应测试 |
| 空问卷也能发布 | 发布前检查至少一道题 |
| 跳转后统计分母错误 | 保存 `visitedQuestionIds`，分别计算访问人数和回答人数 |
| 双击/重试可能重复入库 | `submissionToken` 幂等键 + 唯一索引 |
| 匿名身份无法严格去重 | 会话哈希做尽力限制；严格要求时要求登录 |
| PyMongo explain 响应出现 UTF-8 解码错误 | 测试连接使用 `CodecOptions(unicode_decode_error_handler="replace")`，成功取得执行计划 |


## 9. 当前限制

当前适合中小规模使用。题目暂不支持编辑和拖动排序；规则界面一次配置一个条件；统计按需聚合，尚未做物化缓存；没有图表、Excel 导出和答卷逐条删除。
