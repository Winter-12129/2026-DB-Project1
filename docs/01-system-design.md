# 基于 MongoDB 的问卷系统：系统设计

版本：0.1  
日期：2026-10-20  
状态：第一阶段初始设计，待功能需求与数据库设计细化

- 系统由哪些模块组成。
- 每个模块负责什么，不负责什么。

- `02-功能需求.md`：逐模块的用户故事、业务规则和验收标准。

## 2. 设计目标与原则

### 2.1 模块化单体

系统采用一个应用、一个数据库的模块化单体结构，不采用微服务。每个业务模块有独立目录、路由、服务逻辑和数据访问边界，但可以作为一个整体部署。

这样可以同时获得：

- 比单文件更容易维护和测试。
- 比微服务更低的部署和调试成本。
- 第二阶段可以在模块内部扩展，不必重写整个系统。

### 2.2 单一职责

账号、问卷管理、题目、逻辑跳转、发布分享、答卷填写、统计结果各自成为独立模块。每个模块只处理自己的业务规则，不替其他模块做决定。

### 2.3 稳定核心，隔离变化

以下内容属于稳定核心，第一阶段就要定清楚：

- 用户身份和权限判断。
- 问卷状态机。
- 题目、选项和答案使用稳定 ID。
- 提交时的校验顺序。
- 条件规则的求值顺序。
- 统计百分比的分母语义。
- 已发布问卷和答卷的版本关系。

以下内容属于可变化边缘，通过扩展点隔离：

- 新题型。
- 新条件操作符和跳转动作。
- 新统计图表。
- 新导出格式。
- 新登录方式。

### 2.4 服务端权威

浏览器端可以计算题目可见性、做即时提示，但最终校验必须由服务端完成。用户不能通过修改 JavaScript 或直接构造请求，提交不可见题目的答案，或绕过必填规则。

### 2.5 渐进式演进

第一阶段不追求把所有功能做满，而是做一个可运行的端到端闭环，并保留第二阶段的扩展点。扩展时应优先新增文件和注册处理器，而不是修改提交、统计等主流程。

## 3. 角色与系统边界

| 角色 | 主要能力 |
|---|---|
| 访客 | 打开分享链接、填写已发布问卷、提交答卷 |
| 注册用户 | 注册、登录、创建和管理自己的问卷，也可以填写他人的问卷 |
| 问卷所有者 | 问卷创建者，可编辑草稿、发布、关闭问卷、查看统计和导出结果 |

系统负责执行状态、时间、权限和校验规则，不是一个独立的人类角色。

第一阶段不包含：

- 组织、团队、多人协作编辑。
- 复杂管理员后台。
- 问卷模板市场。
- 支付、配额和商业化功能。
- 实时协同编辑。
- 复杂的用户画像和推荐。

## 4. 总体架构

```text
浏览器
  ├─ 创建者控制台：Jinja2 页面 + 原生 JavaScript
  └─ 公开填写页：Jinja2 页面 + 原生 JavaScript
          │
          │ HTTP / JSON
          ▼
Flask 应用层
  路由、请求解析、会话、响应格式
          │
          ▼
应用服务层
  用例编排、权限检查、状态检查、事务边界
          │
          ▼
业务模块
  账号与权限 | 问卷管理 | 题目 | 逻辑与跳转
  发布与分享 | 答卷填写 | 统计与结果
          │
          ▼
仓储层
  PyMongo 查询与写入
          │
          ▼
MongoDB
```

横切能力包括：配置、错误处理、日志、输入校验、时间处理、安全策略。

架构上的关键约束：

- 路由层不直接操作 MongoDB。
- 业务模块通过服务接口协作，不直接读取其他模块负责的集合。
- 模块之间传递 DTO，不把 MongoDB 原始文档直接暴露给前端或其他模块。
- 领域逻辑尽量不依赖 Flask 的 `request`、`session`，由路由层把当前用户和输入传进来。

## 5. 模块划分

模块边界是代码和业务职责的边界，不等于数据库集合边界。例如，题目可能物理上内嵌在问卷文档里，但题目编辑、校验和题型扩展仍然由题目模块负责。最终采用内嵌还是独立集合，由下一阶段的数据库设计决定。

| 编号 | 模块 | 主要职责 | 概念上拥有的数据 | 主要依赖 |
|---|---|---|---|---|
| M0 | 公共基础 | 配置、数据库连接、错误、日志、分页、通用工具 | 无业务数据 | 无 |
| M1 | 账号与权限 | 注册、登录、退出、当前用户、所有者校验 | 用户身份和登录状态 | M0 |
| M2 | 问卷管理与生命周期 | 问卷元数据、草稿、编辑、状态机、关闭 | 问卷基本信息和状态 | M0、M1、M3、M4 |
| M3 | 题目 | 题目定义、题型、选项、排序、答案校验 | 题目和选项定义 | M0 |
| M4 | 逻辑与跳转 | 显示条件、跳转规则、规则校验、服务端求值 | 条件规则和跳转规则 | M0、M3 |
| M5 | 发布与分享 | 发布编排、分享码、公开访问、链接失效 | 分享码和公开访问策略 | M0、M1、M2、M3、M4、M6 |
| M6 | 答卷填写与提交 | 填写流程、答案收集、提交校验、重复提交控制 | 答卷和答案 | M0、M1、M2、M3、M4 |
| M7 | 统计与结果 | 单题统计、答卷列表、导出、访问控制 | 统计结果和导出结果 | M0、M1、M2、M3、M6 |

### 5.1 M1 账号与权限

职责：

- 用户注册、登录、退出。
- 密码哈希和登录会话。
- 提供当前用户身份。
- 校验某个用户是否是某份问卷的所有者。

不负责：

- 问卷业务规则。
- 答卷重复提交策略的业务判断。
- 页面权限的具体展示逻辑。

主要操作：

- 注册账号。
- 登录和退出。
- 获取当前用户。
- 要求当前用户是问卷所有者。

扩展点：

- 第三方登录。
- 邮箱验证。
- 找回密码。
- 更细的角色和权限。

边界说明：其他模块只向账号模块询问“当前是谁”和“他是否有权操作”，不在自己的代码里重复实现登录和密码逻辑。

### 5.2 M2 问卷管理与生命周期

职责：

- 创建问卷草稿。
- 修改标题、说明等基本信息。
- 列出当前用户的问卷。
- 管理问卷状态。
- 发布前的问卷级检查。
- 关闭问卷。

不负责：

- 单个题目的编辑和校验。
- 条件规则的具体求值。
- 分享码的生成。
- 答卷统计。

主要操作：

- 创建草稿。
- 更新基本信息。
- 获取所有者视角的问卷。
- 列出我的问卷。
- 检查是否满足发布条件。
- 将问卷标记为已发布。
- 关闭问卷。

状态归属：M2 是问卷状态的唯一所有者。其他模块不能直接修改状态，只能调用 M2 的状态转换操作。

扩展点：

- 归档。
- 复制问卷。
- 定时发布和定时关闭。
- 模板。

### 5.3 M3 题目

职责：

- 维护题目定义：题干、题型、选项、必填、排序。
- 为题目和选项分配稳定 ID。
- 校验题目定义是否合法。
- 根据题型校验和规范化答案。
- 为统计模块提供题型相关的聚合描述。

不负责：

- 判断某道题在当前答案下是否可见。
- 保存答卷。
- 决定页面如何渲染。

主要操作：

- 新增、修改、删除题目。
- 调整题目顺序。
- 校验题目定义。
- 校验某道题的答案。
- 列出某份问卷的题目。

扩展点：

- 题型注册表。
- 新题型处理器。
- 题型对应的前端渲染器。

边界说明：题目模块可以内嵌在问卷文档中存储，但“谁能改题目、题目如何校验”仍由 M3 统一负责。新增题型时，应主要是新增题型处理器和注册，而不是修改答卷提交主流程。

建议第一阶段支持的题型：

- 单选。
- 多选。
- 单行或多行文本。
- 评分。

最终题型清单由下一阶段功能需求确认。

### 5.4 M4 逻辑与跳转

职责：

- 定义题目显示和隐藏条件。
- 定义题目或页面之间的跳转。
- 校验规则引用是否合法。
- 防止规则形成环。
- 在服务端计算当前可见题目和下一步位置。
- 为提交校验提供“哪些题应当可见”的结果。

不负责：

- 题目本身的定义。
- 页面样式和动画。
- 保存答案。

规则的概念结构：

- 目标：哪道题或哪一页。
- 条件列表：引用哪道题、使用什么比较方式、期望什么值。
- 匹配方式：全部满足或任一满足。
- 动作：显示、隐藏或跳转。

关键规则：

- 条件和跳转使用题目稳定 ID，不使用数组下标。
- 只允许引用排在前面的题目，从结构上避免循环依赖。
- 发布前必须校验悬空引用、不可达目标和非法动作。
- 服务端重新计算可见性，再校验答案。
- 隐藏题目的答案在提交时丢弃，或明确标记为不可见；两种策略必须统一。

扩展点：

- 新比较操作符。
- 新动作，例如跳转到指定页、直接结束问卷。
- 更复杂的匹配方式。

第一阶段可以先实现题目显示和隐藏，但规则存储结构和求值接口必须能容纳后续的题目跳转和分页跳转。

### 5.5 M5 发布与分享

职责：

- 编排发布流程。
- 生成唯一的分享码。
- 提供公开访问入口。
- 根据问卷状态决定链接是否可用。
- 处理关闭后的公开页面。
- 为未来重新生成或撤销链接预留能力。

不负责：

- 创建问卷内容。
- 编辑题目。
- 计算条件规则。
- 保存答卷。

发布编排流程：

1. 校验当前用户是问卷所有者。
2. 通过 M2 检查问卷是否处于草稿状态。
3. 通过 M3 校验题目定义。
4. 通过 M4 校验条件和跳转规则。
5. 生成唯一、不可预测的分享码。
6. 通过 M2 将问卷状态改为已发布，并记录分享码。
7. 返回公开访问链接。

任何一步失败，问卷都保持原状态。

扩展点：

- 访问密码。
- 仅登录用户可填写。
- 链接过期时间。
- 重新生成或撤销链接。
- 二维码。
- 自定义短链接。

### 5.6 M6 答卷填写与提交

职责：

- 为公开填写页提供已发布问卷。
- 计算当前可见题目。
- 收集和规范化答案。
- 校验必填、类型、选项范围和可见性。
- 控制重复提交。
- 保存答卷并记录问卷版本。
- 返回提交结果。

不负责：

- 统计图表。
- 修改问卷内容。
- 生成分享链接。

主要操作：

- 获取填写视图。
- 提交答卷。
- 查询某份问卷的答卷是否存在。

重复提交策略的基线：

- 登录用户：同一问卷默认只能提交一份，使用账号身份判断。
- 匿名用户：使用签名 Cookie 或浏览器标识做尽力而为的限制，不能声称绝对可靠。
- 具体策略在功能需求阶段确认。

扩展点：

- 暂存草稿。
- 断点续填。
- 文件上传。
- 配额和名额限制。

### 5.7 M7 统计与结果

职责：

- 按题目汇总统计。
- 计算选项数量和百分比。
- 处理多选题、文本题和评分题。
- 提供答卷列表。
- 导出结果。
- 校验只有问卷所有者可以查看。

不负责：

- 修改答卷。
- 修改问卷。
- 决定题目的校验规则。

关键统计口径：

- 单选题：按选项计数，未选择的选项也要显示为 0。
- 多选题：先展开数组，再按选项分组。
- 文本题：保留原文列表，不在第一版强行做词云。
- 百分比分母：使用“看见这道题的答卷数”，不是全部答卷数。

扩展点：

- 图表。
- 交叉分析。
- 按时间或用户属性筛选。
- 更多导出格式。

### 5.8 M0 公共基础

职责：

- 配置和环境变量。
- MongoDB 客户端入口。
- 统一错误格式。
- 日志和请求标识。
- 分页。
- ID 和时间工具。
- 通用校验工具。

边界说明：M0 不是“什么都可以往里放”的杂物间。业务规则必须留在对应业务模块。

## 6. 模块依赖与调用规则

| 模块 | 允许依赖的模块 |
|---|---|
| M0 公共基础 | 无 |
| M1 账号与权限 | M0 |
| M2 问卷管理与生命周期 | M0、M1、M3、M4 |
| M3 题目 | M0 |
| M4 逻辑与跳转 | M0、M3 |
| M5 发布与分享 | M0、M1、M2、M3、M4、M6 |
| M6 答卷填写与提交 | M0、M1、M2、M3、M4 |
| M7 统计与结果 | M0、M1、M2、M3、M6 |

调用规则：

1. 路由层只调用应用服务，不直接访问数据库。
2. 跨模块调用只通过公开的服务接口和 DTO。
3. 一个模块不直接读写另一个模块负责的集合。
4. 业务模块不直接依赖 Flask 的请求对象；当前用户和输入由路由层传入。
5. 不允许为了省事形成双向依赖。需要反向通知时，由上层应用服务编排。
6. 新增功能优先在目标模块内部完成，避免把逻辑塞进公共模块。

## 7. 关键业务流程

### 7.1 创建和编辑草稿

1. 用户登录。
2. M1 提供当前用户。
3. M2 创建问卷草稿并设置所有者。
4. 用户通过 M3 添加、修改和排序题目。
5. 用户通过 M4 配置显示和跳转规则。
6. 保存失败时，已有草稿内容不能被部分覆盖。

### 7.2 发布问卷

1. 创建者请求发布。
2. M5 校验所有权和当前状态。
3. M2 检查问卷级发布条件。
4. M3 校验所有题目定义。
5. M4 校验所有条件和跳转规则。
6. M5 生成分享码。
7. M2 将状态改为已发布。
8. 返回公开链接。

发布是一个整体用例。校验失败时，不生成分享码，不改变状态。

### 7.3 访客填写问卷

1. 访客访问 `/s/<分享码>`。
2. M5 解析分享码。
3. M2 返回已发布问卷。
4. M3 提供题目定义。
5. M4 计算当前可见题目。
6. 页面渲染填写界面。
7. 访客提交答案。
8. M5 再次解析分享码并确认状态。
9. M6 重新计算可见性，校验答案，丢弃隐藏题答案。
10. M6 保存答卷并记录问卷版本。
11. 返回提交凭证或成功页面。

### 7.4 查看统计

1. 创建者登录。
2. M1 校验当前用户身份。
3. M7 校验问卷所有权。
4. M7 读取答卷，按题型聚合。
5. 返回统计结果和答卷列表。

### 7.5 关闭问卷

1. 创建者请求关闭。
2. M2 校验所有权和当前状态。
3. M2 将状态改为已关闭。
4. 公开链接显示“问卷已关闭”。
5. 新的提交被拒绝，已有答卷和统计保留。

## 8. 问卷状态机

| 状态 | 含义 | 允许的关键操作 |
|---|---|---|
| DRAFT | 草稿，仅所有者可见和编辑 | 编辑基本信息和题目、配置规则、发布、删除草稿 |
| PUBLISHED | 已发布，可通过分享链接填写 | 查看统计、关闭；默认不允许直接修改内容 |
| CLOSED | 已关闭，不再接受新答卷 | 查看已有统计；默认不允许重新开放 |

状态转换：

| 当前状态 | 操作 | 目标状态 | 条件 |
|---|---|---|---|
| 无 | 创建 | DRAFT | 已登录用户 |
| DRAFT | 发布 | PUBLISHED | 所有者操作；至少一道题；题目和规则校验通过 |
| PUBLISHED | 关闭 | CLOSED | 所有者操作 |
| DRAFT | 删除 | 无 | 所有者操作；未产生公开链接 |
| CLOSED | 重新发布 | PUBLISHED | 第一阶段不做，第二阶段再评估 |

状态规则：

- 状态只能由 M2 修改。
- 发布后默认冻结问卷内容，避免新答卷和旧答卷对应不同题目。
- 如果第二阶段需要“发布后编辑”，应增加问卷版本快照，而不是直接覆盖旧内容。
- 关闭不等于删除。关闭后仍保留答卷和统计。
- 已发布问卷不直接物理删除，避免历史答卷失去关联。

分享链接与状态的关系：

| 问卷状态 | 访问分享链接的结果 |
|---|---|
| DRAFT | 不可公开访问，返回未找到或无权限 |
| PUBLISHED | 显示填写页面，接受提交 |
| CLOSED | 显示已关闭页面，不接受提交 |

## 9. 分享链接设计

### 9.1 链接格式

公开链接使用：

```text
/s/<分享码>
```

分享码是服务端生成的 URL 安全随机字符串，要求：

- 唯一。
- 不可预测。
- 不直接使用数据库 ObjectId。
- 不包含用户隐私信息。
- 长度足够，避免被枚举。

### 9.2 生命周期

- 发布时生成。
- 已发布期间保持不变。
- 关闭后链接仍然存在，但显示已关闭页面。
- 重新生成链接会使旧链接失效，第一阶段不做，第二阶段作为扩展。

### 9.3 版本关系

第一阶段基线：发布后内容不可直接修改。  
如果第二阶段支持修改已发布问卷，采用版本快照；分享链接默认指向最新已发布版本，答卷记录提交时的问卷版本。这样旧答卷仍然可以按照旧版本解释。

## 10. 模块服务契约

以下是概念级接口，具体函数签名和参数在编码阶段确定。

| 服务 | 主要操作 |
|---|---|
| AuthService | 注册、登录、退出、获取当前用户、要求所有者权限 |
| SurveyService | 创建草稿、更新基本信息、按所有者查询、列出我的问卷、标记发布、关闭 |
| QuestionService | 新增、修改、删除、排序、校验定义、校验答案、列出题目 |
| LogicService | 校验规则、计算可见题目、计算下一步、校验提交 |
| PublishingService | 发布、解析分享码、关闭公开访问 |
| ResponseService | 提交答卷、按问卷查询答卷、统计数量 |
| AnalyticsService | 汇总统计、导出结果 |

跨模块数据传输规则：

- 使用明确的 DTO，不直接传 MongoDB 文档。
- 题目和选项使用稳定 ID。
- 时间统一以 UTC 存储，展示时转换为本地时间。
- 接口错误使用统一结构，至少包含错误码和人类可读信息。
- 对外 JSON API 使用 `/api/v1` 前缀，便于后续演进。

## 13. 非功能设计

### 13.1 安全

- 密码只存哈希，不存明文。
- 登录使用服务端会话 Cookie。
- 所有创建者接口都要校验所有权。
- 公开提交接口做限流和请求体大小限制。
- 文本答案渲染时防 XSS。
- 分享码不可预测，避免枚举。
- 日志中不记录密码、会话令牌和完整答卷内容。

### 13.2 数据完整性

- 服务端是最终校验者。
- 题目和选项使用稳定 ID。
- 答卷记录问卷版本。
- 提交时只接受可见题目的答案。
- 数据库层在下一阶段增加必要的结构校验和唯一索引。

### 13.3 性能

- 列表接口分页。
- 统计优先使用聚合查询。
- 只建立服务真实查询的索引。
- 避免在页面循环中逐题查询数据库。
- 数据量增大后再考虑预聚合，不在第一版提前复杂化。

### 13.4 可靠性与并发

- 一次答卷提交尽量只写一个文档，减少对多文档事务的依赖。
- 需要“一人一份”时，用唯一索引做最终防线。
- 重复点击提交要有幂等或重复检测策略。
- 发布流程失败时保持原状态。

### 13.5 测试

- 规则求值：表驱动单元测试。
- 统计口径：固定答卷数据的聚合测试。
- 模块协作：服务层集成测试。
- 接口契约：请求和响应结构测试。
- 关键路径：创建、发布、填写、查看统计的端到端测试。

## 15. 第一阶段验收标准

系统设计达到以下标准，才可以进入功能需求和数据库设计：

- 每条作业要求都能找到明确负责的模块。
- 每个模块都有清晰的“负责”和“不负责”边界。
- 模块依赖方向明确，没有双向依赖。
- 问卷状态转换和分享链接行为没有歧义。
- 已发布问卷的内容策略明确。
- 条件逻辑和统计口径被当作核心业务规则，而不是页面技巧。
- 第二阶段增加题型、规则动作或统计图表时，能指出具体扩展位置。
- 数据库设计可以依据本文的模块职责和概念数据所有权继续展开。

## 16. 下一阶段需要确认的决策

以下问题在功能需求和数据库设计阶段确认，本文先给出建议基线：

| 决策 | 建议基线 |
|---|---|
| 第一版题型 | 单选、多选、文本、评分 |
| 是否允许匿名填写 | 允许；登录填写作为可选策略 |
| 一人一份如何限制 | 登录用户用唯一约束；匿名用户用 Cookie 尽力限制 |
| 发布后能否改题 | 第一阶段不能；需要修改时复制为新草稿，第二阶段再做版本化编辑 |
| 跳转范围 | 先做题目显示和隐藏，再扩展题目跳转和分页跳转 |
| 统计导出格式 | 先支持 CSV |
| 已发布问卷能否删除 | 不物理删除，只关闭 |
| 数据库部署方式 | 本地 MongoDB 或 MongoDB Atlas，开发阶段二选一 |

这些决策确定后，再编写每个模块的详细功能需求和 MongoDB 数据库设计，避免在系统结构尚未稳定时过早锁死字段。
